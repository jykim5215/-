# 동기 재생 가상 시뮬레이션

목표: **지연은 최소로, 여러 스피커의 소리는 같은 순간에.** 실기기 없이 이 목표를 재기 위해
**실제 앱 코드를 그대로 컴파일**해 가상 기기·가상 Wi-Fi 위에서 돌린다.

```bash
bash audiobridge/sim/sync/run.sh            # 10분 + 지연별 3분씩 (수 분 걸림)
bash audiobridge/sim/sync/run.sh --quick    # CI용 짧은 실행
bash audiobridge/sim/sync/run.sh --diag     # 기기별 시계 오차·소리 시각 오차 진단 추가
```

## 돌리는 실제 코드

| 파일 | 역할 |
|---|---|
| `net/ClockSync.kt` | 소스 시계 → 수신 시계 오프셋·속도 차 추정 |
| `audio/PlayoutScheduler.kt` | 샘플 단위 재생 판단 (무음/건너뛰기/1~2샘플 빼기·반복) |
| `audio/CaptureTimeline.kt` | 송신 타임스탬프 = 첫 샘플이 녹음된 시각 |
| `audio/JitterBuffer.kt`, `net/Protocol.kt` | 수신 버퍼, 패킷 규약 |
| `baseline/ClockSyncV28.kt` | 비교용 v2.8 원본 시계 동기 |

기존 재생 판단(ModeAPlayer의 5ms 프레임 판단)은 `SyncSim.kt`의 `legacyStep`에 그대로 옮겨 비교한다.
Windows(C#)는 같은 알고리즘을 옮긴 것이다(`windows/PlayoutScheduler.cs`·`ClockSync.cs`·`CaptureTimeline.cs`) —
Kotlin 판을 바꾸면 C# 판도 똑같이 바꿔야 한다.

## 가상 세계 (가정값 — 실측이 아님)

- **기기**: 폰A(출력 버퍼 20ms, 스피커 내부 2.3ms), 폰B 보급형(40ms, 9.1ms), Windows PC(30ms, 1.4ms).
  기기마다 단조시계 ±30ppm, 오디오 칩 −35~+80ppm, 재생 헤드 관측 잡음 σ 150~400µs, 가끔 스레드 선점(1~8ms).
- **송신**: 캡처 드라이버가 20ms씩 몰아서 넘겨주고 read 완료가 0.3~1.5ms(가끔 3~12ms) 늦는다. 하드웨어 캡처 시각은 ±80µs.
- **Wi-Fi** (링크마다 순서 보장, 손실 포함):

| 프로필 | 기본 | 지터(중앙값) | 스파이크 | 멈춤(stall) | 손실 |
|---|---|---|---|---|---|
| 좋은 5GHz | 1.5ms | 0.7ms | 0.1%, 5–20ms | 0.02회/s, 10–30ms | 0.1% |
| 보통 가정 | 2.5ms | 1.5ms | 1%, 10–60ms | 0.1회/s, 30–120ms | 0.5% |
| 혼잡·절전 | 3ms | 3ms | 2%, 20–150ms | 0.3회/s, 50–300ms | 2% |

## 결과 (전체 실행, 보통 가정 Wi-Fi, 공통 지연 600ms, 10분)

| 구성 | 싱크 오차 중앙값 | p99 | 최대 | 지연 탓 끊김/분 |
|---|---:|---:|---:|---:|
| 현재 앱(v2.8) 그대로 | 8.32ms | 12.60ms | 16.70ms | 24.75 |
| 현재 앱 + 스피커 지연 수동 보정(1ms) | 2.35ms | 6.51ms | 9.23ms | 23.84 |
| 새 방식, 보정 없음 | 7.62ms | 7.93ms | 8.15ms | 0 |
| 새 방식 + 보정(1ms 단위, 현재 UI) | 0.45ms | 0.98ms | 1.17ms | 0 |
| **새 방식 + 정밀 보정** | **0.26ms** | **0.76ms** | **0.96ms** | **0** |
| 새 방식(하드웨어 캡처 시각 없는 기기) + 정밀 보정 | 0.25ms | 0.70ms | 0.90ms | 0 |

- 하드웨어 캡처 시각만, 샘플 단위 판단만 넣으면 오히려 나빠지거나(분당 2,861회 끊김) 개선이 작다 — **셋이 함께** 필요하다.
- 스피커 내부(DSP) 지연은 OS가 모르므로 어떤 알고리즘도 못 맞춘다(보정 없음 7.6ms). 기기별 추가 지연으로만 맞출 수 있고,
  현재 UI의 1ms 단위는 기기당 최대 0.5ms 반올림 오차를 남긴다.

지연 탓 끊김이 없는 최소 공통 지연 (새 방식 + 정밀 보정, 3분씩):

| 네트워크 | 최소 공통 지연 | 녹음→소리 | 싱크 p99 |
|---|---:|---:|---:|
| 좋은 5GHz | 100ms | 104ms | 0.34ms |
| 보통 가정 | 200ms | 204ms | 0.82ms |
| 혼잡·절전 | 450ms | 454ms | 1.45ms |

지연의 바닥은 **가장 큰 출력 버퍼(40ms) + 캡처 묶음(20ms) + Wi-Fi 멈춤 꼬리**다. 0ms는 물리적으로 불가능하다.
패킷 손실로 인한 끊김(분당 수십 회, 손실률에 비례)은 지연을 늘려도 줄지 않는다.

## 한계

- Wi-Fi·기기 수치는 공개 자료 수준의 **가정**이다. 실제 집 Wi-Fi 꼬리 지연은 다를 수 있다.
- 오디오 경로는 샘플 단위 시각만 본다. 1샘플 빼기/반복의 음질 영향(거의 들리지 않음)은 재지 않는다.
- 스피커 내부 지연 보정은 "잰 값을 추가 지연으로 넣었다"고 가정한다 — 앱의 자동 음향 맞춤은 아직 공통 지연만 고른다.
- Windows는 C# 판이 아니라 같은 알고리즘의 Kotlin 판으로 돈다.
